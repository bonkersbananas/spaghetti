# 0028. OAuth for the MCP server is a small implementation on D1, and a connected app is an agent

Status: Accepted

**Decision:** `/mcp` accepts tokens from the OAuth flow the MCP specification asks for, so Claude's apps (claude.ai custom connectors, which also reach the iPhone app) connect with a sign-in instead of a pasted token: protected resource metadata (RFC 9728), authorization server metadata (8414), dynamic client registration (7591), the authorization code flow with PKCE (S256 only) and refresh tokens (rotated on every use), and revocation (7009). It is about 400 lines in `src/worker/oauth/`, on D1, with no new binding or secret. The consent screen is the app's own `/authorize` page and uses its sign-in (password or passkey). An approved app becomes an agent of that person ("Claude for Alex") whose access tokens are ordinary `agent_tokens` rows (an hour long, `spg_…`, stored hashed), so scopes, "via", the change feed and every existing bearer token behave exactly as before. Disconnecting it on the Agents page deletes its refresh tokens and revokes its access tokens at once.

**Why not a library:** Cloudflare's `workers-oauth-provider` wraps the whole Worker and keeps its grants, clients and tokens in a KV namespace, which would be a new binding for local development, the container and Cloudflare, a second store beside D1, and a second kind of token for the API to understand. Here the pieces are small (a code table, a refresh table, a client table), and reusing `agent_tokens` means revocation, the Agents page and "via" needed nothing new. The price is that we maintain the protocol code ourselves; the tests walk every step, including the refusals.

**Choices:** public clients with PKCE are the norm; a client that registers with a client secret gets one (stored as a hash). Registration is open (the protocol needs it) so the table is capped and unused clients are cleared after a day. Redirect addresses must be https, plain http only to localhost, or an app's own scheme, and must match exactly. A request that names no scope (or only ones we don't know) asks for all four, which the consent screen lists in plain words; people approve or decline as a whole rather than picking scopes. Access tokens last an hour and refresh tokens sixty days, each use making a new one; one agent per person and app, so connecting again picks the same "Claude for Alex" up. Typed-in tokens (Agents page, `pnpm agent:add`) are unchanged and never expire.

**Consequences:** no ship step beyond the usual `pnpm ship`, which applies migration 0027 and deploys; `/oauth/*` and `/.well-known/*` are routed to the Worker (`run_worker_first`). The daily cron tidies expired codes and tokens. A client that needs something we don't offer (OpenID Connect discovery, client authentication by signed JWT, the implicit flow) can't connect.
