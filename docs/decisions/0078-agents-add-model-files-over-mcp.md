# 0078. Agents add model files over MCP; the next browser reads them

Status: Accepted (extends [0004](0004-photos-resized-in-the-browser.md), [0014](0014-mcp-hand-written-stateless.md) and [0046](0046-models-are-sliced-in-the-browser.md))

**Decision:** An agent can put a model into Spaghetti with the MCP tool `add_file`: an `.stl` or `.3mf` (a plain model, a Bambu Studio or Orca project, or a sliced `.gcode.3mf`) to an idea or build (`build_id`), an attempt's slicer file (`attempt_id`, replacing the one it has) or a twist's model (`twist_id`, replacing its model), by `file_url` (https, the open internet only, on every hop, as `photo_url`) up to 25 MB, or `file_base64` up to 10 MB. Scopes are the REST routes': `capture` for an idea, build and twist, `attempts` for an attempt; the tool still calls Spaghetti's own API with the caller's token. Removing stays for people. A twist's model route (`PUT /twists/:id/file/:fileId`) now takes the `capture` scope.

**What the Worker reads, and what waits.** The Worker never slices and never draws. It reads what is cheap and safe from the bytes: a file's type (an STL's triangle count, or an ASCII STL's facets; a 3MF's zip header), an STL's bounding box (told back to the agent so it can check its model's size), and, for a sliced `.gcode.3mf`, its plate, settings, objects and plate picture from the zip's small config entries (`shared/threemf/read.ts`, never the G-code). A model is stored as a `kind=model` row with no slice and no picture, exactly as a model added in the app is before its slice is saved. The first signed-in browser that sees one (`lib/model-read.ts`, as `lib/photo-resize.ts` does for photos) slices it quietly in idle time, one at a time, with the app's own slicing jobs, which save the slice, its sliced file and its plate picture; from then on it has its cover, 3D view and "Slice with…" like any model. Only models an agent added are taken up: a person's unsliced model still offers "Slice it" and waits for them. The server hands out one claim at a time (`POST /files/:id/read-claim`, ten minutes, as a photo's resize), a tab takes a Web Lock per file, and a failed attempt is not repeated for five minutes. A phone, a connection that saves data and a hidden tab leave the job (a slice running when the tab hides is stopped, its claim lapsing). The engine failing on the model is saved as a failed slice (this device not getting the model or the engine isn't), so no device tries it again; and a failure from a background read (`quiet=1`) never replaces a good slice.

**An agent never destroys a person's work.** `attempt_id` and `twist_id` replace the file there; an agent's request is refused (409) when the file there was added by a person, who removes it in the app first (the simpler choice over keeping it restorable). A file's id belongs to one file, whatever its kind: every upload route refuses another file's id, and an agent's `POST /uploads` one that exists. A file an agent puts on an attempt fills in its empty settings from what the file or its slice says (not the pantry's spools or the build's parts).

**Marked as the agent's.** Every file row (`item_files`, `attempt_files`, `twist_files`) has `created_via`, the agent's id as attempts and ideas do, shown in the API as `createdVia`; the change feed names the agent as the actor, and a build's story (`get_build`) says "added via Claude for Alex" and that the app slices a model the next time it is open. The app draws no new mark: files are not signed in the app, and neither are photos.

**Pictures.** `add_photo` (and `capture_idea`, `log_attempt`, `finish_attempt`) also take a PNG, since renders of a model come as PNG. It is kept as it came and flagged `needsResize` like any agent photo; the browser that resizes it makes the WebP or JPEG copies, which replace it. Only a photo flagged `needsResize` may be a PNG: every other photo route still takes WebP and JPEG. Twists have no photos of their own (they lead with their idea's), so there is no twist photo tool.

**Not built, proposed:** a one-time upload address for agents with a shell (Claude Code `curl`ing a large file to a URL valid for a few minutes) on top of `/uploads`. It would need a signed, short-lived, single-file token outside the bearer scheme and a place in the scopes table; `file_url` (the agent puts the file anywhere public for a minute) and the base64 argument cover models made in a conversation, which are small.

**Consequences:** a model made in a conversation lands in the app in one call and is ready, without anyone doing anything, once the app is opened. The 25 MB and 10 MB caps keep the Worker's memory (the bytes, their copy in a form and the file) well under its limit; bigger files are for people in the app (up to 250 MB).
