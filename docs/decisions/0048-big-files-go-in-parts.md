# 0048. Files up to 250 MB go to R2 in parts

Status: Accepted

**Decision:** Models (`.stl`, plain `.3mf`), slicer files (`.gcode.3mf`) and a model's sliced `.gcode.3mf` are kept up to 250 MB (`MAX_MODEL_FILE_BYTES`, `MAX_SLICER_FILE_BYTES`), on ideas, builds and attempts alike. A file up to 32 MB (`ONE_REQUEST_FILE_BYTES`) still goes in the one multipart request that carries its details. A bigger one is sent first in parts through the Worker, as an R2 multipart upload (`routes/uploads.ts`): `POST /api/uploads` starts it for the key `files/<id>/file` (or `…/sliced`), each part (32 MiB, all equal but the last; `UPLOAD_PART_BYTES`) is `PUT` and streamed into R2 as it arrives, and `…/complete` puts them together and checks the size. The file's row is saved afterwards, as before, with `uploaded=1` in place of the bytes, and is refused (409 `upload_incomplete`) unless the object is in the bucket at the size the row says: a row exists only once the whole file does. The browser (`lib/big-upload.ts`) sends the parts one by one, each retried up to four times with a growing wait; what was sent is kept in memory, so another go (a tap on the card, or the outbox's own retry for an attempt's file) carries on from the next part; a refusal drops the upload. Every route is idempotent on the client's ids: a part sent again replaces itself, `complete` asked again after a lost answer finds the finished object of the right size and says so. Cards show the percent while it goes; if it stops, the card says "Didn't finish saving. Your file is still here." with Try again, and the browser asks before the tab is closed. On a phone (a touch screen), a file over 100 MB is kept all the same, but isn't read, sliced or drawn there: its card says so in one line (a model gets the "ran out of memory on this phone, it will finish on a laptop" line that slicing already had), and a laptop that shows it finishes the slice by itself.

**Why:** Carl Oscar asked (Nov 13) for larger `.stl` / `.3mf` / `.gcode.3mf` files than the old 50 MB and 25 MB caps, 250 MB for now. A Worker request body is limited to 100 MB on the Free and Pro plans, and the Worker's memory is 128 MB, so one request can't carry such a file, and `formData()` can't hold it.

**Alternatives:** Presigned R2 URLs for direct upload: needs S3 credentials, a bucket CORS rule and a second way of reaching R2, which breaks local workerd and Docker, where only the binding exists. A table of uploads in D1: the uploadId R2 gives is enough state, and nothing is kept for a file that is never saved. Resuming after a reload: the file's bytes are only in the tab (or, for an attempt, in the outbox, which starts over), so parts already sent are not worth remembering across pages.

**Consequences:** An upload that is never finished costs nothing to clean up: R2 aborts incomplete multipart uploads by itself after 7 days (it is a default of the service, and wrangler config has no setting for it), so there is no cron sweep of our own; a failed or given-up upload is aborted at once by the browser, and a finished one whose row is then refused is removed with `DELETE /api/uploads/:id/file`, which only removes bytes that no row owns. `part: "sliced"` stays for people only; a token needs `capture` or `attempts` for `part: "file"`, like the file routes. Reading a 3MF on a desktop holds the file in memory (a 202 MB zip took 0.25 s and about 490 MB of memory in Node), which is fine on a laptop and why a phone doesn't. Keeping a big file in the outbox (IndexedDB) depends on the device's storage; if the browser refuses it, the file is lost with the attempt's other queued things, as for any big blob before.
