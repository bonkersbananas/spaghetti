# 0071. Printables models are read from its public API, by the Worker or through Claude's fetch

Status: Accepted (amends [0019](0019-claude-drafts-ideas-from-model-pages.md) and the drafts part of [0067](0067-the-scout-sees-a-link-alive-through-the-api-or-claudes-fetch.md))

**What happened:** a Printables link didn't draft (November 16, 2026: "Claude couldn't read that page"). Both runs recorded `not_readable` with `unread: challenge` and `fetchErrors: ["url_not_accessible"]`: the Worker's fetch of the page got Cloudflare's bot challenge (403, `cf-mitigated: challenge`) and so did Anthropic's web fetch. The day before, another Printables idea drafted through the web fetch, which got through that time, but none of its four pictures was stored: the page named PNG thumbnails (`…/thumbs/cover/800x800/png/….png`, 1.6 MB each), which the photo pipeline refuses.

What was checked (November 16, from the sandbox, a data-centre address, and from a throwaway Worker on Cloudflare's edge in CPH):

- Printables' web app reads a model from its public GraphQL API, `https://api.printables.com/graphql/`, with no sign-in. It answers POST with a JSON body, and GET with `query` and `variables` in the address. A model gives its name, summary, description (HTML), tags, category, designer (`user.publicUsername`), licence (`license.name`, `abbreviation`), pictures (`images.filePath`, under `https://media.printables.com/`) and, when the designer filled them in, printer, materials, nozzle sizes, layer heights, weight (g) and print time (decimal hours). A number that isn't a model answers 200 with `{"data":{"print":null}}`. Introspection is off, so the query names only fields seen to answer.
- From the sandbox the API answered 200 every time. From the Worker it answered 429 `Request was throttled.` every time, with Django's own headers: Printables throttles by client address, and Workers' outbound requests to another Cloudflare site share a few addresses, so the limit is always used up. Browser-like headers changed nothing, and nothing was done to get around the limit. The page and its `__data.json` and oEmbed are challenged; `api.printables.com` sends no CORS headers to other origins, so a person's browser can't read it for the app either.
- `media.printables.com` serves the Worker fine. It keeps pictures as uploaded (a 9 MB JPEG, a 6 MB PNG) and makes resized WebP thumbnails at `<folder>/thumbs/inside/<box>/<original extension>/<name>.webp`, for boxes 320x240, 1280x960, 1600x1200 and 1920x1440 (other sizes answer 400).

**Decision:** a Printables model is read from its API, by whatever can reach it, and the facts come from the API's own answer, never from Claude's words:

1. **The Worker asks the API first** (POST, that one address, no redirects, a size cap and a timeout), before the page, which a Worker never gets. While Printables throttles Workers this fails at once with `apiUnread: http_429`, but it costs one small request, and it is the whole read wherever Printables answers.
2. **Otherwise Claude's web fetch is handed the API's GET address** next to the page's, and told the page is usually closed to it. Web fetch takes addresses of at most 250 characters (`url_too_long`, Anthropic's docs), so this address is a short query of its own, about 195 characters: `https://api.printables.com/graphql/?query=%7Bprint(id:1577248)%7Bname,summary,description,user%7BpublicUsername%7D,license%7Babbreviation%7D,images%7BfilePath%7D,materials%7Bname%7D,weight%7D%7D` (no quotes round the number, commas for spaces, only the braces escaped; it stays within 250 even if every comma and colon were escaped too). It leaves out the tags and the settings other than materials and weight, which the Worker's own POST asks for. The answer is taken for the model its address names, since it carries no id. The Worker then reads the API's JSON from the fetch result itself (`source: web_fetch_api`): the title, designer, licence and pictures are the API's, and Claude writes only the note and the print suggestions, as on MakerWorld. Should Claude call that JSON unreadable, it is asked once more with the model as data (`asked: 2`).
3. **A model that doesn't exist is no draft.** When the API says `print: null`, to the Worker or in Claude's fetch, the draft fails (`outcome: not_found`) without Claude being asked or whatever it wrote being used: no draft of a soft "not found". The person sees the usual "Claude couldn't read that page." with Try again. Other sites' "not found" keeps going to Claude's fetch, as before.
4. **Pictures:** every `media.printables.com` picture, an original or one of its thumbnails, is fetched as the WebP thumbnail that fits in 1600x1200 (1280x960 for the scout's smaller pictures), like MakerWorld's `x-oss-process` WebP. The photo pipeline stores it as it stores MakerWorld's, and the browser resizes it later.

The licence reads as its abbreviation ("CC BY-NC-SA", "CC0"). The print settings the API gives go to Claude as one profile line ("material PLA; 29 g of filament; about 2 h 28 min; layer heights 0.15, 0.28 mm; 0.4 mm nozzle; printed on Prusa MK3/S/S+"), from which it fills the material and settings, saying only what is there.

**Amended (November 16, after it shipped):** the first version handed Claude the full query with JSON variables, about 430 characters, and every production run came back `fetchErrors: ["url_too_long", "url_not_accessible"]`. Hence the short address above. Each run now records `apiFetch`: what Claude's fetch made of that address (`read`, the tool's error code, or `not_tried`). The Worker's 429 isn't momentary: every request from the edge got it at 20:00 and again at 21:50 UTC, and production got it at 21:35, 21:41 and 21:45, so retrying with backoff wouldn't help. The API answers `application/json` whatever the request accepts.

**Not verified before it shipped:** whether Anthropic's web fetch reaches `api.printables.com` and gives back its JSON as text (the sandbox has no Anthropic key, and the stand-in can't tell). The docs say the tool reads "only text, HTML, and PDF" and don't say whether `application/json` counts as text. `draft_runs` says which way each Printables draft went: `worker_api`, `web_fetch_api`, or `web_fetch` with `apiFetch` saying why the API's address gave nothing (`unsupported_content_type` would mean JSON isn't read, and then no route is left that doesn't get around Printables' blocking).

**Left out:** a proxy, a headless browser or anything else that would get past Printables' challenge or throttle; the idea scout, which still doesn't suggest Printables models (its check is the Worker's, which Printables throttles).

**Amended (November 18): Printables is closed to us, so the link names the idea and Claude's fetch is no longer asked.** `draft_runs` for Printables links: 12 runs since November 16, none drafted; every one got `url_not_accessible` from Claude's web fetch (for the page and, after the address was shortened, for the API's address: `apiFetch: url_not_accessible`), and the Worker's own API try got `http_429` every time. The only Printables draft that ever worked was on November 15. So the draft stops handing Printables to Claude's fetch (a Claude call each time that cannot work), points 2's address and the second ask are no longer used, and the Worker keeps its one cheap API try (point 1): the day Printables answers a Worker, drafts work again by themselves.

- When the API try gives nothing, an untitled idea is named from the link's slug (`printablesTitleFromLink`: words spaced, first letter capitalised, a few brand words as people write them such as IKEA and USB, cut at a word under 60 characters; none for `/model/<id>` without a slug). Never over a title a person wrote (the write is conditional in the database too). The draft reads `failed` with failure `closed` when the cause is a throttle, a challenge or a refusal (429, 403, 401, 451, no answer from a stand-in), and the idea says "Named from the link. Printables keeps its pages closed to Claude." with no Try again. Failures a retry can fix (the API's 5xx, a timeout) stay `unreadable` with Try again, and are named too. A model the API says isn't there is `not_found` as before and stays untitled. These runs are recorded as `closed` and don't count towards the day's cap, since Claude wasn't called.
- Ideas whose draft failed earlier: the five-minute cron (`nameClosedPrintables`, through `resumeDrafts`) names failed-unreadable Printables drafts whose idea has no title, once, and marks them `closed`. In production on November 18 that is one idea (the Antilop high chair handle, "Carrying handle for IKEA antilop high chair legs"); the other Printables idea already has its title.
