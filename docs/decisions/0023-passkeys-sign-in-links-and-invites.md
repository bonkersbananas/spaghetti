# 0023. Passkeys, sign-in links and invites, all single-use and all in the app

Status: Accepted

**Decision:** People can sign in with a passkey (Face ID, Touch ID, Windows Hello) made in the account menu, sign in on a new device with a single-use link or short code made on a signed-in one, and invite a new person with a single-use link, all without the command line. The password stays as the fallback, and `pnpm user:add` stays for resets. It is still a private notebook: no public sign-up, no roles, and everyone in the workspace is equal.

**Why this shape:**

- **WebAuthn through `@simplewebauthn/server`**, which runs on Workers (WebCrypto, no Node modules); no crypto by hand. Passkeys are discoverable and ask for user verification every time (`residentKey: required`, `userVerification: required`), so the sign-in button needs no username and the browser can offer them in the username field. The relying party comes from `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGINS` (`spaghetti.day` in `wrangler.jsonc`; `localhost` for the dev server, the e2e tests and `pnpm start`, set by `vite.config.ts` for `vite` only, never for a build, and by `--var` for wrangler). Attestation is "none": we want a key, not to vet the maker.
- **Challenges** are random, stored server-side for five minutes, answered once (taken with `DELETE … RETURNING`), and bound to what they were made for: a person's own session for adding a passkey, the invite for joining, nobody for signing in. The counter is checked by the library (a key that counts backwards is refused) and kept up to date with the backup flag.
- **Sign in on another device is a link plus a code, not a push to approve.** A link has a secret in its fragment (`/link#spl_…`), so no server, proxy or analytics sees it; opening it asks for one tap, then signs in and offers a passkey there. A phone camera reads the QR, or the short code (8 characters, no look-alikes) is typed on the new device's sign-in screen. Both are single-use, last ten minutes, and each person has one waiting at a time. The code is guessable in principle, so every attempt is rate limited per IP and wrong codes share a global allowance; the link's 256-bit token is not guessable. The alternative, a "request approval" flow where the new device asks and the old one approves, needs a long-lived waiting state on the new device and a real-time channel; this needs neither, and works when the first device is a laptop and the second a phone with no keyboard to spare.
- **Invites** are 256-bit tokens in a fragment (`/join#spi_…`), single use, good for seven days. Only hashes (SHA-256, like agent tokens) are stored; the link is shown once when made. Claiming the invite is one atomic `UPDATE … WHERE used_at IS NULL AND withdrawn_at IS NULL AND expires_at > now`, so of two people opening it only one gets in; it creates exactly one person and signs in only them. Anyone signed in can see and withdraw a pending invite. A person who joins with a passkey only has no password (`NO_PASSWORD`, which never verifies).
- **Rate limits** are one table (`auth_hits`) and one atomic insert-if-under-limit, like the password change's. Redeeming and joining are limited per IP, passkey sign-in per IP; making links is limited per person.
- **People only.** Everything under `/api/account`, `/api/join` and the sign-in routes is person-only for agent tokens (`403 person_only`, and reads of `/account` too): a token can never add a passkey, make a link or an invite, or see any of them. The signed-in-devices list (the existing `sessions` table) fell out of the same work and is included.

**Consequences:** the first person to join by invite makes three people; there is no cap beyond "someone you invited". A used or expired link or invite shows a calm sentence, not an error page. Removing a passkey waits out its Undo toast before the request is sent, like revoking an agent token. A password reset still goes through `pnpm user:add`. Revisit if a platform's passkeys turn out not to survive a device change (iCloud Keychain and Google Password Manager sync them; a hardware-bound key does not, which the list shows as "backed up" or not).
