# 0022. Claude suggests how a print went from its photo, and only suggests

Status: Accepted

**Decision:** When an attempt that has no outcome yet gets a photo (taken by hand in the attempt sheet or capture, or the printer bridge's camera frame when a print ends), Claude (`claude-opus-5-5` through the official `@anthropic-ai/sdk`, the same key as the drafts of [0019](0019-claude-drafts-ideas-from-model-pages.md)) looks at it and suggests an outcome (Worked, Partly, Spaghetti), the failure tags that fit from the built-in list, a success note when it worked, and one short sentence of why. The answer is constrained to a JSON schema whose tags are an enum of the built-in slugs.

**It only suggests.** The attempt keeps no outcome, tags or note of its own until a person picks one. In the attempt sheet the suggested outcome is hinted on its button ("suggested") and one tap takes it, together with the suggested tags, which are marked "· suggested" like the bridge's suggested tag and are the person's to take off; picking something else is just picking. The reason sits quietly under the buttons. Where the build page asks "off the bed · how did it go?", the matching button gets the same hint and the reason shows under it. Once there is an outcome the suggestion only keeps the tags marked.

**Instant and honest.** Adding the photo never waits on Claude. The attempt shows "Looking at the photo…" (a pulse, not a spinner) and the suggestion arrives through the change feed, also for the other person. If Claude can't tell (the plate before printing, a blurry shot), refuses, or the call fails, nothing is suggested and nothing is in the way; there is no error line at all, the run's row says why. A photo is never read twice; a newer photo's suggestion replaces the older one, while a newer photo Claude can't tell from leaves the older suggestion standing.

**Who and how much.** Hidden without `ANTHROPIC_API_KEY` (`GET /api/features` `photoReads`). People's photos start it, and so does a token with both the `attempts` and `printer` scopes (the bridge's frame); other agent tokens don't. 30 reads a day for the workspace, its own cap (rows of `photo_reads` with `ran_at`, UTC days).

**How the call runs:** after the upload's response, with `waitUntil`, with a 26-second timeout. A glance at one photo at low effort is far shorter than reading a model page, so unlike the drafts it needn't keep a browser request open, which also lets the bridge (which has no browser) start it the same way; locally on workerd it behaves the same. The row of the job (`photo_reads`, one per photo) is the fallback: the 5-minute cron takes a read nobody has worked on for four minutes, twice at most, then marks it timed out. Each row is also the record of the run: model, stop reason, outcome, HTTP status or error type, time taken, never the photo or the prompt.

**What it reads:** the photo's large variant from R2 (already resized in the browser, [0004](0004-photos-resized-in-the-browser.md)). The bridge's frame arrives `needsResize`, with the original stored as both variants; it is read as it is when it is a JPEG or WebP within the API's limits (5 MB, 8000 px), which a camera frame is, rather than waiting for a browser to make a variant. It also gets the build's title and the attempt's note as context, and any failure tag the printer reported.

**Left out:** Today's print card and the push notification (another piece of work was changing Today; both can show the hint later), asking again for a photo that wasn't read, a visible error line, server-side refusal fallbacks.
