# 0076. The app finds the build a print belongs to, says why, and one tap moves it

Status: Accepted (Carl Oscar asked for it on Nov 21, 2026, after the bridge filed his fit-test ring as a new build)

**Decision:** the printer bridge no longer decides which build a print belongs to: it files each print in a build of its own (named after the job), and the Worker places it. A pure matcher (`shared/print-match.ts`) scores the ideas and builds in progress on what a person could check:

- the same file by name, kept with the build or printed in one of its attempts: 60 points. Names are compared without path, extension (`.gcode.3mf`, `.3mf`, `.gcode`, `.stl`), copy suffix ("(2)", " (1)", " copy"), `_plate_N`, accents (UÖBF is uobf), case or separators. A copy's trailing number ("ring-2") is 50, a name sharing most words 25.
- the build's title is the job's name: 45 (most words alike: 20).
- one of its files downloaded (`POST /api/files/:id/downloads`, from any download link) or opened in Bambu Studio (kept when the link is made) before the print began: 45 within 30 minutes, 25 within 3 hours, 10 within a day. Kept a month (`file_downloads`).
- the printer's estimate within 10 % of a file's (bridges from 0.2 send it): 15.
- a build started in the 2 hours before, with nothing printed yet: 10, only on top of something else.

A build with 70 points or more and 30 ahead of the next takes the print, and the printer's build goes (merged: `items.merged_into`, its address answers 308 to the other, so the bridge still finds its print). Otherwise the print stays in its own build, which asks "Which build is this?" (`print_jobs.asking`) with the best three (25 points or more) as offers, until someone answers; of builds as likely, those in progress come before ideas, then the one started last. The reasons are kept (`print_jobs.reasons`) and said in one line ("Filed here: it printed UOBF-fit-test-ring, this build's file. Not this build?"). Only the printer bridge's prints are matched (its agent is the one in the `bridge` row), and names that say nothing ("Untitled", "Model 2", "Part 3") match nothing.

Any attempt can move to another build, an idea (which becomes a build) or its own build (`POST /api/attempts/:id/move`), with its photos, note, outcome, settings, file and Claude's notes. The build the printer made for that print goes with it when nothing else is in it and nobody touched it (its title as the printer gave it, `print_jobs.own_title`; no note, photo, file, part, comment, reaction, live link, person it is for or twist), which is how a printer's build is merged into the right one; any other build stays, whoever made it. A move is one batch claimed by its `attempt_moves` row, which goes in only while the attempt is where the request found it; every other statement runs only if that row is there, so two moves at once never split an attempt from its photos, and the loser is answered 409. "A new build" for a matched print brings back the printer's own build. One Undo (`/unmove`) puts everything back, the question too. The moved attempt says where it came from (`attempt_moves`). Moving and answering are people's: the bridge's token only files its own print.

A print the printer recorded is the printer's, not whoever paired the bridge (Carl Oscar saw his name on a print Marie started). The bridge's agent is marked as the printer (`agents.printer`: set when a pairing makes or reuses it and when an agent first reports as the bridge, kept after it disconnects, backfilled from `bridge_pairings` and `bridge`), and its attempts and the builds it makes name nobody: the printer's mark and "From the printer" stand where an avatar would, on the attempt, the cards on the bed, the Journal, Lately, the week, the build list and the build's own line ("Made by the printer"). A person can say who started a print, later and only if they like (`attempts.started_by`, `PUT /api/attempts/:id/started-by`, people only, with Undo): it then reads "Marie · from the printer", and it stays with the attempt when it moves. Everything that says whose a print is follows the same rule (`creditedTo`): the Journal's and search's person filters, the catch-up (a print nobody has named isn't news of the other person), Claude's story and week note. The "How did it go?" nudge for a print nobody has named goes to both of you, naming neither (as if it were each of yours); once someone is named it follows the usual rule, that person and whoever asked to hear of the other's prints. A build the printer made stays the printer's even once its print is named.

**Why:** the bridge's own rule (the same name as the latest attempt's file) missed Carl Oscar's print twice over: the ring was a file kept with the build, not an attempt's, and Bambu Studio saved its second download as "UOBF-fit-test-ring(2)". The app knows far more than the bridge (kept files, downloads, which build was just started), and a matcher in the Worker improves without a bridge release. Scores and reasons stay simple enough to say in a sentence, so a guess is never a mystery; when two builds fit about as well, asking is cheaper than a wrong guess.

**Consequences:** his case scores 70 (same file, a build started 27 seconds before) and goes straight in; with the Bambu Studio open recorded it is 115. Bridges before 0.2 send only the job's name (as the build's title) and are matched on that; the server takes their attempt into the matched build and keeps their later calls to their own build working wherever the print went since: a bridge's GET of it answers 308 to the build its print is in now (people still see the build), a photo sent there lands with the attempt, and a retried start finds the same attempt. Bridge 0.2 sends `print` (name, plate's G-code file, estimate) with the attempt, follows the print to where the app put it and ends it by its attempt alone; it needs a release. The printer's builds filed in the 30 days before this ask the question once (the migration's backfill). An attempt the printer filed without its file's settings (no USB drive, so no file) now sits beside attempts that have them: what it left out is unknown, not taken away, so its chips never say "no plate set" (`changesSince`).

**Not done:** a mark inside Spaghetti's own sliced files (an exact match when the bridge has the file): the API and matcher take a `fileId`, but writing it means threading the file's id through the slicing worker, and whether Bambu Studio keeps custom metadata when it sends a file to the printer is unconfirmed. Merging builds that have several attempts of their own (comments, files, parts) is not offered: moving their attempts one at a time does it. Done and shelved builds are never matched automatically; they are in the sheet.
