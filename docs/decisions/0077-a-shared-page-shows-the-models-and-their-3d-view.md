# 0077. A shared page shows the models and their 3D view, never the files

Status: Accepted (amends [0075](0075-a-public-link-shows-one-thing-read-only.md))

**Decision:** A public link's page (`/s/<token>`) shows the thing's models as the app's cards show them, read-only, and opens the app's own 3D view of how each will print on a tap. An idea's or build's kept files, each attempt's file and a twist's model each get their card: the plate's picture, what the print takes ("About 1 h 26 min · 13.2 g"), the file's name, its size (to the millimetre), the settings line ("Standard · Everyday strength · No supports · PLA Basic jade white"), the filaments' colours and the card's cautions ("Parts of it float in the air."). A build also shows what it is made of (its parts and how far each is) and what each attempt printed. A card does one thing: the whole of it opens the 3D view (an attempt's file says so, "See how it prints"). Who sliced it isn't said: "Sliced by Spaghetti" on every card means nothing to a friend, and the page's foot says Spaghetti. Comments, reactions, people, "for", wishlists, Up next, Claude's words, the bridge's reports (the 3D view never follows a live print for a guest) and anything that only matters for editing stay out, as in 0075.

**No files.** A guest can't download a model, a sliced file or an original, and there is no "Open in Bambu Studio": many models come from MakerWorld or Printables under licences that forbid passing the files on. The 3D view needs bytes, so it gets the plate's toolpaths and nothing more: `/s/<token>/files/<id>/toolpaths` answers a zip of its own with that plate's G-code, copied from the stored `.gcode.3mf` by R2 range reads as it is compressed (`worker/guest/toolpaths.ts`; never inflated, so it costs the Worker almost no CPU), and the two small configs the viewer reads, inflated and written anew with only what it reads (the plate's time, its filaments' colours, types and nozzles: a desktop slicer's settings can hold a print host's password and paths in someone's home folder, its slice info every plate's objects). A file whose directory lists an entry twice gets nothing. The G-code's own config block still goes with it (the slicer's settings, preset names and notes, a post-processing script's path; never a print host's secrets, which the slicers leave out): docs/security.md says what it holds. The model's mesh (`3D/3dmodel.model`, about half of a sliced file), the other plates and the pictures stay behind: a guest's browser never receives the model, and a phone fetches about half as much. The address refuses a navigation, a download or another site's page (`Sec-Fetch-Mode`/`-Dest`/`-Site`), so pasted into an address bar it is the same 404 as anything else; it has no `Content-Disposition`. The toolpaths are still G-code an X2D could print: that is what a 3D view of a print is.

**The plate's picture** comes through `/s/<token>/files/<id>/thumb`, with a slicer's own text chunks (a PNG's `tEXt`, `iTXt`, `zTXt`, `eXIf`, `tIME`…) stripped as a photo's metadata is (`stripPhotoMetadata` now reads PNGs, keeping only the chunks that draw the picture and say its colours).

**Access** is 0075's: a token reaches only its one thing. A file is served only when the page lists its card (`fileIdsOf` in `guest/view.ts`) and, checked again against the database, it is that thing's own live file (an idea's or build's, a live attempt's of it, or the twist's model) on a live thing behind a live link; anything else, another thing's file, a deleted file or attempt, a stopped link, another part (`file`, `sliced`, `previous`), is the same 404. GET and HEAD only. `Cache-Control: private, max-age=300`, as photos.

**How it is built: (a), the Worker's page with one small script.** The page stays HTML rendered by the Worker (hono/jsx, escaped), photos first and with no script needed to read it; the cards are HTML too, their words from the same shared functions the app's card uses (`shared/slicing/card.ts`, `slicedBy`, `slicingSummary`, `standInSentence`, `problemSentence`), so a guest reads what the two people read. The page's one script (`src/guest/island.ts`, about 2.5 kB gzip with Vite's preload helper) opens the sheet on a tap (on a phone a bottom sheet with the app's handle, which a finger pulls down to close, as vaul does; vaul itself would mean loading React before the sheet could open) and fetches the viewer as a finger nears a card: the app's own `PrintViewer` with React and three.js (`src/guest/viewer.tsx`: about 235 kB gzip of script, 7 kB of styles and the 10 kB toolpath worker, then the toolpaths: for one of Carl Oscar's 5 to 6 MB sliced files, roughly what is left once a mesh like its 3.4 MB original stays behind). A guest who never taps downloads none of it. The page has its own Vite build (`scripts/vite-guest.ts`), run after the app's into `/assets/guest/`, so the app's chunks and first load don't change (in one build React would move out of the app's entry into a shared chunk). Its policy: `script-src` and `worker-src` only `<origin>/assets/guest/`, `connect-src` only `<origin>/s/<token>/files/`, nothing inline but styles (React sets the viewer's few inline styles), no frames, forms or base.

**Why not (b), a client-rendered share view on a token-scoped API that reuses the app's components:** it would need React, the card components and the app's styles (over 100 kB gzip) and an API round trip before the first photo could start loading, where the Worker's page sends the photo with the HTML; the app's model card and attempt entry are built for editing (slicing jobs, settings sheets, the spools and printer queries, `/api` addresses), so a read-only mode would be threaded through code the two people use every day; and a JSON API for guests is one more surface to keep to the allow-list. What (a) copies by hand is the cards' markup and styles (`worker/guest/page.tsx`, `src/guest/guest.css`); the words and the viewer, the parts that change most, are the app's own.

**Why:** Carl Oscar (Nov 21), after trying the first links: "A linked idea / build / twist page when linking to a user that isn't logged in should also show the models, and the 3D view that shows how it'll be printed. Basically most things that we see when logged in, but they cannot change anything, so just a share view where they can see what we're working on. We'll just use this to share this with friends and family, so it's really nothing secret that's shared."

**Consequences:** the shared page has a script now (0075's "no script at all" is replaced by "one script, from its own build, only for the 3D view"). A plate's picture is shown where 0075 showed none, and files appear as cards where 0075 hid them; the files themselves stay private. Someone determined can still keep the toolpaths their browser fetched: they are what the 3D view draws. A new field on a file row stays private until `guestFile` in `guest/view.ts` adds it. Revisit if guests should see the model's own colours switch, a plate's other plates, or the print following the printer live.
