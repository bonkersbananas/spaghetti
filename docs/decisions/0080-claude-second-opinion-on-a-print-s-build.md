# 0080. Names count forgivingly, earlier prints count, and Claude gives a second opinion on a print's build

Status: Accepted (Carl Oscar asked for it on Nov 24, 2026, after a print named like eleven earlier prints of one build was offered to an unrelated idea). Amends [0076](0076-the-app-finds-the-build-a-print-belongs-to.md).

**Decision:** the matcher (`shared/print-match.ts`) changes in three ways, and when it still can't place a print Claude is asked once for a second opinion.

- **Names are read forgivingly.** On top of 0076's comparison, filler the slicer or a person adds ("print", "final", "copy"), and copy numbers left anywhere at the end ("…-v3(4)-print" is "…-v3"), are dropped (`looseKey`): such a name is the file's own copy, 50 points. Without versions, bare numbers and plurals (`coreKey`: "markers" is "marker", "v3" goes), the same words are a file "named much like it" (25) and the build's own name (45: "Lamp shades" for "lamp-shade-v2-final").
- **Earlier prints count.** The names the printer gave the prints already in a build (`print_jobs.name` of its attempts, wherever they were filed first) are compared like files: the same name (copies and filler aside) is 55, much like it 30. "Same name as attempt 7" says why.
- **An unrelated file opened just before counts for little.** A file downloaded or opened in Bambu Studio before the print whose name shares no word of what it is about with a named print's (versions, numbers and filler aside) was most likely meant for another print: 10 points within 30 minutes, nothing later. A print with no meaningful name, or a file whose name agrees, keeps 0076's points. Of a build's sends, the one that says the most counts.

**Claude's second opinion.** When the bridge files a print the matcher doesn't place (no match, so it asks "Which build is this?"), the Worker asks Claude once, after the response (`worker/print-match/`): the print's name, plate, filaments in the trays, the printer's estimate and when it began, and up to 30 builds and ideas (those the matcher found something for first, then builds in progress and ideas, latest touched first), each with its title, files, earlier prints' names, attempts, when it was last touched, what was taken away before the print and what the matcher made of it. Claude answers with one of them, or none, and a few words of why. Its pick leads the "Is this …?" question wherever it is asked (Today, the Journal, the printer's page, the build page, the "How did it go?" sheet) with the line "Claude thinks so: <why>"; the matcher's other suggestions follow. It never places the print: the print stays nobody's until a person says Yes (0076), and its pick never counts toward a match.

Each run is one row in `print_match_runs` (the attempt, the ids it was shown, its pick and reason, how the run went and the diagnosis: model, stop reason, HTTP status, time), which is also the "once". The model and setup are the photo read's (0023: Opus 5.5, low effort, the answer constrained to a schema whose picks are only the keys it was shown), and at most 30 runs a day count against the cap (`cap` rows record the ones skipped). Without `ANTHROPIC_API_KEY`, past the cap, when Claude names none or the call fails, nothing changes: the matcher's suggestions stand.

**Why:** a print named "…-glass-marker-v3(4)-print" scored nothing for the build whose eleven earlier prints and files carried that name ("-print" and the "(4)" in the middle hid it), while an idea's file opened in Bambu Studio 54 minutes before scored 25 and was offered first. The name fixes place such prints without Claude; Claude is for the prints whose names the rules can't read (a renamed project, an abbreviation), where a person would know at a glance.

**Not done:** Claude never answers for a print the matcher matched, nor for prints filed before this (the backfill asks no one). Its pick isn't shown while the call is running (the question shows the matcher's first until the answer arrives, a few seconds later). The cron doesn't retry a run whose Worker was recycled mid-call; its row stays `asking`.
