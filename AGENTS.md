# Working on Spaghetti

Spaghetti is a private 3D printing notebook for two people. Design quality is the main requirement: read [docs/design.md](docs/design.md) before writing any UI, and look at `/styleguide`.

Before proposing or building something, check what is already decided: [docs/decisions/](docs/decisions/README.md) has one short record per settled decision, including the things we decided **not** to do (one printer, no public sign-up, nothing depends on a Bambu service, offline is read-only…), and [docs/roadmap.md](docs/roadmap.md) says what the phases, specs and pull request numbers in commit messages refer to and what comes next. When a decision is made in a conversation, a review or an issue, add a record (the format is in the decisions README). **When a pull request finishes something on the roadmap, tick it there in the same pull request** (and add what it turns up); the roadmap is a copy that drifts otherwise.

## Stack

- Cloudflare Worker (Hono) for `/api`, D1 through Drizzle, R2 (`PHOTOS`) for photos. Locally it all runs on workerd via `@cloudflare/vite-plugin`; there is no Node server.
- React 19 SPA: Vite, TanStack Router (file-based) and TanStack Query, Tailwind CSS v4 with our tokens, `motion`, `vaul`, `sonner`, Phosphor icons.
- Tooling: pnpm, TypeScript (strict), Biome, Vitest (`@cloudflare/vitest-plugin` for the Worker), Playwright.

The Worker must stay Workers-native: no `fs`, no native modules, no image libraries (photos are resized in the browser before upload). Add `nodejs_compat` to wrangler.jsonc only if a dependency truly needs it.

### Setting up a sandbox

Node 24 or later is required (the scripts run TypeScript with Node's own type stripping; `pnpm run doctor` says so if yours is older). Bare `pnpm doctor` is pnpm's own command: run ours as `pnpm run doctor`. The Playwright browser is `pnpm exec playwright install chromium-headless-shell`. Where that download is blocked, or a Chromium is already installed, point `SPAGHETTI_BROWSER` at its executable and `pnpm screenshots`, `pnpm screenshots:compare`, `pnpm test:e2e` and the doctor all use it:

```sh
SPAGHETTI_BROWSER=/usr/bin/chromium pnpm screenshots
```

## How to…

### Scaffolding

`pnpm new route <name>`, `pnpm new component <Name>` and `pnpm new endpoint <plural-name>` create the files below with their wiring (add `--dry-run` to preview; run `pnpm new` without arguments for the options). Then fill them in, `pnpm format`, and run the checks.

- `route`: the route file, `e2e/<name>.spec.ts` (it opens), a screen in `scripts/screenshot-routes.ts` and the regenerated `routeTree.gen.ts`; with `--section` or `--workshop` also the entry in `sections.ts` and its shortcut in `shared/shortcuts.ts`.
- `component`: `components/<--in ui>/<Name>.tsx` and its styleguide section (`routes/_app/-styleguide/<name>.tsx`, the one place for sections, listed in `styleguide.tsx`'s table of contents and page). The templates are in `scripts/lib/scaffold.ts`.
- `endpoint`: `worker/routes/<name>.ts` with a zod schema, mounted in `app.ts`, the types in `shared/api.ts`, a `queryOptions` in `lib/queries.ts` and `test/worker/<name>.test.ts`. Storage (a table and migration) is yours to add.

If a wiring step can't find its place (a file moved), the command says what to add by hand.

### Add a page (route)

1. Create `src/client/routes/_app/<name>.tsx` (signed-in) or `src/client/routes/<name>.tsx` (public) with `createFileRoute`. The router plugin regenerates `routeTree.gen.ts` when Vite runs (`pnpm dev` or `pnpm build`); commit the regenerated file.
2. Start the page with `<PageHeader title=… subtitle=… />`, and give it an `EmptyState` and skeletons before it has data.
3. If it is a top-level section, add it to `components/shell/sections.ts` (sidebar, hotkeys and the palette read `sections`; the phone tab bar reads `tabs`, which stays at four places around the capture button, so a new section usually goes in the sidebar only).
4. Add it to `scripts/screenshot-routes.ts` so `pnpm screenshots` captures it.

### Add an API endpoint

1. Add a router in `src/worker/routes/<resource>.ts` (`new Hono<AppEnv>()`), using `c.var.db` (Drizzle) and `c.var.user` (the signed-in person).
2. Mount it in `src/worker/app.ts`. Routes mounted after `.use(requireAuth)` need a session or a token; `test/worker/auth-guard.test.ts` walks every route and fails for one that answers without them, unless it is on its public list (add it there only on purpose, and say why in [docs/security.md](docs/security.md)).
3. Put request/response types in `src/shared/api.ts`; validate input with zod; return errors with `apiError(c, status, code, message)`.
4. Call it from the client through `api()` in `src/client/lib/api.ts`, wrapped in a `queryOptions` in `lib/queries.ts`. Mutations update the cache optimistically (`onMutate`) and roll back on error, so taps feel instant.
5. Test it in `test/worker/` with `request()` and `signIn()` from `helpers.ts`; call `resetDb()` in `beforeEach` (storage is shared by the tests in a file).

### Add a migration

1. Change `src/worker/db/schema.ts`.
2. `pnpm db:generate --name <what-changed>` writes `migrations/NNNN_<what-changed>.sql`. Read it; commit it with `migrations/meta/`.
3. `pnpm db:migrate` applies it locally (`pnpm dev` does too). Tests apply all migrations automatically. Remote: `pnpm ship` applies them before deploying (see docs/deploy.md).

Never edit a migration that has been merged; add a new one.

### Items and photos

- An idea is a row in `items` with `stage = "idea"`; phase 3 moves the same row through `building`, `done`, `shelved`. Photos are their own table (`item_id`, `position`, size, average `color`, `taken_at`), stored in R2 as `photos/<id>/large` and `/thumb`.
- The client picks ids (UUIDs) for items and photos, so every write is idempotent and safe to retry. New captures and added photos go through `outbox` (never straight to the API): it shows them at once, persists them in IndexedDB and sends them in the background. `useIdeas()` / `useItem()` merge the server's data with what the outbox still holds.
- Deletes are soft (`deleted_at`); restore endpoints are the undo. `purgeDeleted` removes rows and R2 objects 30 days later, from the daily cron.
- Photos are never processed in the Worker: resize in the browser with `processPhoto` (lib/images.ts). A photo that arrives without a browser (an agent, the printer bridge) is uploaded with `needsResize=1`: it is stored as is, `photos.needs_resize` is set, its R2 objects are marked `provisional` (served `no-cache`, never kept by the service worker) and `lib/photo-resize.ts` has the next browser resize it in idle time and upload the real variants (the claim endpoint `POST /api/photos/:id/resize-claim` keeps two people from both doing it).

### Builds and attempts

- A build is an item with `stage` building, done or shelved (`startedAt`, `finishedAt`, and `coverPhotoId` for the final photo). `PATCH /api/items/:id { stage }` moves it and sets those dates; moving back to `idea` is the undo of "start building". The client keeps ideas and builds in two cached lists (`ideasQuery`, `buildsQuery`); `patchCachedItem` moves an item between them when its stage changes.
- A print finished with no connection goes through the outbox as a `finish` (`outbox.addFinish`, `POST /api/attempts/:id/finish`): the server only fills what is empty and keeps someone else's outcome; `finishedBy` on the attempt says who finished it.
- Attempts (`attempts` table) belong to an item; logging one on an idea makes it a build. `outcome` is null while printing. `settings` is one JSON object (`AttemptSettings` in `src/shared/attempts.ts`) whose names match the .3mf reader's output, so phase 5 can prefill it. Without `settings`, the server copies the previous attempt's ("same as last time", minus results such as actual time or where it failed); the client prefills the sheet the same way with `carryOver`. Each attempt comes back with `changes`, from `describeChanges`, which the client recomputes for optimistic edits.
- Photos may belong to an attempt (`attemptId`); they are still the item's photos, and hidden while their attempt is deleted. New attempts go through the outbox, before their photos, so a photo never uploads ahead of its attempt.
- Failure tags and success notes are slugs; the built-in ones are in `src/shared/attempts.ts` (from docs/printer.md), people's own in the `tags` table (`/api/tags`). Labels can change without a migration.

### Pantry, printer and slicer files

- Spools (`spools`) are the filament library; `ams_slots` says which spool is in which slot ("A1" to "D4", "Ext"), one slot per spool; `printer` is one row (`x2d`) with the setup as JSON (`PrinterSetup` in `shared/spools.ts`). A spool's label photo is stored like other photos (`photos/<id>/…`, served by `/api/photos`), but its fields live on the spool row. Claude can read the label from that photo ([0031](docs/decisions/0031-claude-reads-a-spool-label-from-its-photo.md)): `worker/label-read/` (`claude.ts` the call and the cleaning of what it says, `run.ts` the job rows in `label_reads`, filling only empty fields, the confirmation of several spools); the spool's `fromLabel` lists what it filled and a person's edit takes a field off. The stand-in Claude (`scripts/lib/fake-claude.ts`) picks its answer by a word in the spool's brand, colour or note (`slow`, `broken`, `refused`, `unreadable`, `partly`, `two`).
- Filament in grams ([0009](docs/decisions/0009-filament-tracked-in-grams.md)): grams left are never stored, they are worked out from the net weight, the latest weighing (`spool_weighings`) and the finished attempts' `filaments[].grams` (`shared/ledger.ts` pure rules, `worker/ledger.ts` loading). Spools without gram data keep their hand-set level; with it, `remaining` is derived and a PATCHed one is ignored. Anything that changes an attempt's outcome, filaments or existence must refresh the `spools` queries (outbox handlers, `saveAttemptChanges`, `deleteAttempt`).
- An attempt's filaments keep their plain values (type, brand, color) and add `spoolId` when picked from the pantry, so attempts read the same if the spool goes. `GET /api/spools/:id/attempts` finds them with `json_each` over the settings.
- Slicer files (`attempt_files`, one live per attempt) are read in the browser (`shared/threemf`); the client sends what it read (`prefill`), the plate's PNG and, under `MAX_SLICER_FILE_BYTES` (250 MB), the bytes, through the outbox behind the attempt (`files` in an outbox entry). A file over `ONE_REQUEST_FILE_BYTES` (32 MB) is sent in parts first (`routes/uploads.ts`, `lib/big-upload.ts`, [0048](docs/decisions/0048-big-files-go-in-parts.md)) and its row says `uploaded=1`; item files, the outbox and `lib/slicing/jobs.ts` (the sliced file) all go through `uploadInParts`. R2 keys are `files/<id>/file` and `/thumb`, served at `/api/files/:id` and `/api/files/:id/thumb` only while the file, its attempt and its build are live. The purge removes them with their attempt.
- A model (`kind` "model": an `.stl`, or a `.3mf` with no G-code) is a file row like a slicer file's, in either table, sliced in the browser ([0046](docs/decisions/0046-models-are-sliced-in-the-browser.md)): its bytes are the original (`files/<id>/file`, up to `MAX_MODEL_FILE_BYTES`, always sent), and `PUT /api/files/:id/sliced` (people only) adds the sliced `.gcode.3mf` as a second part (`files/<id>/sliced`, served at `/api/files/:id/sliced`), the plate's picture, what the reader made of it (`prefill`, `objects`, `slicer`) and `slice` (how it went: settings, or the problem). The purge removes all its parts. A model keeps the slicing settings people chose (`slicing`, `PATCH /api/files/:id`) and, after a re-slice sent with `keep=previous` (not one sent in parts, already over it), the slice it replaced for one undo (`previous_slice`, `files/<id>/previous` and `previous-thumb`, `POST /api/files/:id/sliced/restore`) ([0049](docs/decisions/0049-a-model-keeps-its-settings-and-one-slice-to-undo.md)); its settings open from the card in `components/builds/SliceSettings.tsx` (lazy). The engine is a separate program served at `/slicer/<version>/` ([docs/slicer.md](docs/slicer.md)); never import it into the app's code.

### Journal and search

- The journal (`GET /api/journal`) is one SQL query over every event (attempts, ideas captured, builds started, finished, shelved), newest first, paged with a keyset cursor; the client groups it by month, then day (last 7 days) or week (`groupJournal` in `shared/journal.ts`). Filters live in the URL.
- Search is an FTS5 table, `search`, written by hand in `migrations/0003_search.sql` (drizzle-kit doesn't know virtual tables, so it isn't in `schema.ts`; routes query it with raw SQL through `c.env.DB`). Triggers on `items` and `attempts` keep it up to date; the `search_attempt_docs` view says what an attempt's row contains. If you add a column that should be searchable, add a migration that recreates the view and triggers and refills the index, and point `scripts/db-export.ts` at it.
- `shared/search.ts` turns a query into an FTS5 MATCH (every word quoted, prefix matching, PLA/PA/PC/ABS as whole words, tag labels mapped to slugs) and highlights matches on the client the same way.
- `wrangler d1 export` refuses databases with virtual tables: use `pnpm db:export`.

### Change feed and live updates

- Every write to data people see records one row in `changes` (`seq` is the cursor; `entity`, `entityId`, `itemId`, `action` created/updated/deleted/restored, `actorKind`/`actorId`, `at`) and `GET /api/changes?after=<cursor>` serves it to signed-in people (types and the documented shape in `src/shared/changes.ts`). No `after` gives only the feed's current end; `reset` means a cursor can't be followed and everything should be refetched. The daily cron prunes rows older than a month (never the newest).
- The change is written in the same D1 batch as the write: `db.batch([write, recordChange(db, {...}), ...])`. `recordChange` inserts only `WHERE changes() > 0`, so a write that did nothing (a retried capture, a second delete) records nothing, and statements after it can chain on `afterChange` (e.g. bump the item's `updatedAt` only if the change was recorded). A new write path must do this too; `test/worker/changes.test.ts` has one test per kind of write.
- Photos, attempts and files carry the `itemId` they belong to; the pantry and the printer have none. The actor is `{ kind: "person", id }` from `actorOf(c.var.user)`; agents will use `kind: "agent"` with their name, so don't assume a user id.
- The client (`lib/live.ts`, started in `_app.tsx`) polls every 10 s while the tab is visible and online, and at once on focus, on coming back to the tab and when the connection returns; the first answer only learns the feed's end. `refresh` maps changes to query keys: a new query root that other people's writes can change needs a case there. At most one quiet toast for the open screen; a deleted item closes its screen.
- Autosaved fields must follow the server only when untouched (`useFollowServer`) and must send only what this screen changed (`useItemFields`; `useLiveFields` for a form of several fields, as on the spool page and the printer setup), or they undo the other person's edit.

### OpenAPI and webhooks

- **OpenAPI** ([docs/api.md](docs/api.md#the-openapi-document)): `GET /api/openapi.json` is built per caller from `worker/openapi/operations.ts` (one row per route: summary, the zod schema the route validates with, the answer's schema, its other refusals), `schemas.ts` and the scope table in `auth/scopes.ts` (scopes are never repeated by hand). **A new route needs a row there**: `test/openapi/document.test.ts` fails for a route without one (and for a row without a route) and validates the result as OpenAPI 3.1. Export the route's zod schemas (`export { createThing }` at the end of the file) and import them in `operations.ts`. That test lives in `test/openapi` (run by the Node `unit` project, typechecked with the worker's types) because the validator compiles code, which workerd forbids.
- **Webhooks** ([0025](docs/decisions/0025-webhooks-signed-from-the-cron.md), payload and signature in docs/api.md): `webhooks` and `webhook_deliveries` tables, `routes/webhooks.ts` (people only), `webhooks/deliver.ts`. `runWebhooks` (the cron, and after every write that went through, in `waitUntil`; `WEBHOOKS_ON_WRITE=off` in the Worker tests) fans the change feed out into deliveries (one per change per webhook, idempotent) and sends what is due with a lease, retries on 1 m, 5 m, 30 m, 2 h, 6 h, 12 h, then marks the webhook failing. Targets pass `checkWebhookUrl` (the link-preview rules, plus DNS over HTTPS on each delivery); `WEBHOOKS_ALLOW_LOCAL=1`, set only for e2e and screenshots, lets them go to the stand-in receiver in `scripts/lib/fake-claude.ts` (`/hooks/ok`, `/hooks/broken`, `GET /hooks`). Worker tests stub `fetch` (see `test/worker/webhooks.test.ts`) and walk the cron's clock by passing `now`.
- The client side is lazy: `routes/_app/agents.tsx` loads `components/agents/Webhooks.tsx` (the section, `WebhookCard`, `WebhookSheet`, `lib/webhooks.ts`) after the page, so the Agents route's first load stays small. The styleguide's Webhooks section shows the cards and the sheet.

### Keyboard shortcuts and the command palette

- Every shortcut is an entry in `src/shared/shortcuts.ts` (id, group, label, keys). Bind a handler to its id with `useHotkeys({ buildLog: fn })` (`lib/hotkeys.ts`); pass `undefined` when it would do nothing right now. Never match `event.key` by hand in a screen for a shortcut people should know about: add it to the registry so `?` lists it. Show hints with `shortcutCaps(id)`.
- Hotkeys are ignored while typing in a field or with a dialog open (`⌘K` works in fields). Keys inside a field (Enter to save in the capture note) are field behavior, not shortcuts.
- Screens offer actions to the command palette with `useScreenActions("This build", [{ id, label, icon, shortcut?, keywords?, run }])` (lib/palette.tsx); a detail screen also calls `useRememberItem` so it shows under "Recent". General actions and "Go to" rows live in `components/shell/CommandPalette.tsx`. A new top-level section appears in the palette from `sections.ts`.
- There is no palette or shortcut list on phones (`useIsDesktop`).

### The landing page

`/` is the app for someone signed in and `landing.html` for everyone else (`src/worker/home.ts` picks by the session cookie; [0035](docs/decisions/0035-a-landing-page-at-the-root-for-visitors.md)). The page is static, light only, and imports nothing of the app's (its own `src/landing/landing.css` on the tokens, one small `landing.ts`); its files go to `assets/landing/`, out of the service worker's precache, and the app's build output stays byte for byte the same (`scripts/vite-landing.ts`). Its pictures are made by `pnpm landing:shots` from the screenshot seed, with additions from `scripts/landing/demo.ts` (real print photos in place of some drawings, which screens to take): run it after changing the app's screens, and see [docs/landing.md](docs/landing.md) for how to add a picture. The two people appear only in its app screenshots, as M and CO with their pictures (`PEOPLE` in demo.ts, which renames the seed's Alex and Sam for these shots only); the page's own words say what happened, not who. It is tested in `e2e/landing.spec.ts`.

### Add a binding (KV, queue, …)

Declare it in `wrangler.jsonc`, run `pnpm types` to regenerate `worker-configuration.d.ts`, and commit both.

### Add a component or token

1. Shared UI goes in `src/client/components/ui/`, built only from tokens. If you need a new color, size, shadow or duration, add it to `styles/tokens.css` (light **and dark**) and to the `@theme` block. New text/surface pairs go into `scripts/lib/contrast.ts`, which `pnpm test` checks for WCAG AA in both themes. Look at your component in dark mode (the switch on `/styleguide`).
2. Show it in the styleguide: in the matching section file under `routes/_app/-styleguide/` or a new one built from `./shared`'s `Section` and `Panel` (`pnpm new component` makes it), and list a new one in `styleguide.tsx`'s `toc` and page.
3. Document it in `docs/design.md`.
4. Icons: add the Phosphor icon to `components/ui/icons.tsx` and import it from there.

## Measuring speed

`pnpm perf` (scripts/perf.ts, helpers in scripts/lib/perf.ts) seeds a throwaway app, serves the production build and prints medians at 390 px with touch, 4× CPU and slow 4G: cold start (first visit, service worker without saved data, installed app resumed) and input-to-next-paint (Event Timing) plus tap-to-result for the common taps. CDP network throttling doesn't reach the service worker's own `/api` fetches, so resumed numbers leave out network time. `pnpm build:report` prints the bundle breakdown. The first-load ceilings that fail a pull request are in `e2e/first-load.spec.ts` (a screen is held to its ceiling only where the change made it heavier than main); the timing budgets are in `e2e/performance.spec.ts`, which CI runs on main only. Lessons: a `lazy()` component needs its own `<Suspense>`, or the whole screen waits for its chunk (the idea card's menu cost every first visit to Ideas 300 ms); the shell opens from the remembered session and checks it in the background; the Latin Fraunces file is pinned and subset (see app.css) and both Latin faces are preloaded in index.html.

## Design rules

- Tokens and shared components only. No hex colors, `rgb()`, arbitrary sizes like `text-[13px]` or one-off shadows in components: `pnpm lint` fails on them (`scripts/check-design.ts`). Phosphor imports outside `icons.tsx` fail Biome.
- When a screen needs something the system lacks, add it to the system and the styleguide instead of styling it in place.
- Every screen works one-handed on a phone (tab bar, sheets, 44 px targets) and with a keyboard on desktop (sidebar, shortcuts, columns).
- No full-page spinners (skeletons), no save buttons (autosave with `SaveStatus`), no confirm dialogs for deletes (`toast.undo`).
- The pasta jokes stay small: empty-state titles, a toast, the mark.
- Accessible by default: name controls by their visible text (no `aria-label` on cards or rows with text), 44 px touch targets (`touch-target` for smaller controls), fields at 16 px on phones, `m.*` not `motion.*`, and `scrollBehavior()` for JS scrolling. Add new screens to `e2e/screens.spec.ts` (it fails until a new route is there).

## Screenshots

`pnpm screenshots` seeds a throwaway local D1 (the same data as `pnpm dev:seed`: two people, a dozen ideas, the pantry, builds with histories), starts the dev server, signs in and saves each screen in `scripts/screenshot-routes.ts` at 390×844 and 1440×900 into `screenshots/`. Pass names to take only some (`pnpm screenshots ideas capture`). Shots can open a sheet first (`prepare`) or capture the full page (`fullPage`).

- It takes every shot even when one fails, lists the failures at the end and exits 1. A failed shot is a bug in the shot or in the screen: fix it, don't skip it.
- Each theme and width is taken on its own freshly seeded app (about half a minute of seeding each), so a shot that changes data, such as finishing a print, can't leak into the next one.
- The seed's dates count back from a fixed date (`SEED_NOW` in `scripts/seed/index.ts`) and the browser's clock and time zone are fixed to it, so a screen looks the same on any day. Write shots that don't depend on how much data fits a page or on today's date (the journal's "September" shot scrolls until the month appears).
- Options: `--dark` or `--both` (light and dark in one run, files named `ideas-dark-390.png`), `--built` (the production build with its service worker: what offline screens really show), `--iphone` (the Home Screen app's insets), `--webkit` (Safari on an iPhone 17 Pro, 402×874, in WebKit: install it once with `pnpm exec playwright install webkit`; files named `ideas-webkit-402.png`; WebKit is not in CI or the Playwright projects), `--width 402` or `375` (any width under 768 is a phone), `--out DIR`, `--scale 1` (device pixel ratio; the default is 3 on the phone and 2 on the desktop, so a full page can be 1170×9000).
- `pnpm dev:seed` is the same data for exploring by hand; the seed is in `scripts/seed/`, and a new feature that needs data on screen adds to it.

### Showing a change in a pull request

Full-size shots are heavy, so don't publish them all. Run `pnpm screenshots:compare` (light and dark; `--light`, `--base <ref>`, `--scale 2`, or screen names narrow or sharpen it). It takes the shots on `origin/main` and on your working tree, and writes to `screenshots/compare/`:

- `contact/contact-<width>[-dark].png`: one picture per width and theme with every screen small and labeled; changed screens are outlined.
- `changed/<screen>-<width>[-dark].png`: for each screen that changed, before, after and the diff in one picture, cropped to the change. `diff/` has the diff alone.
- `summary.md`: what changed, is new or failed, and the exact `fctl publish` command.

Look at the contact sheets and the changed screens yourself at both widths and fix what looks off or generic, then publish the contact sheet and the changed screens (not `base/` and `head/`) with `fctl publish` and put them in the pull request description, saying what each shows. A pull request that changes no UI should show no changed screens: that is the check.

### Before asking for review

Run the **design-reviewer** subagent (`.claude/agents/design-reviewer.md`; in Claude Code, ask for it by name or use the Agent tool with `subagent_type: "design-reviewer"`) on the screenshots of a UI change: give it the folder or the files and a line on what changed. It reads `docs/design.md`, looks at the screenshots and lists where they break the rules or look generic, most important first; it never edits code. Fix the findings that are right, and say in the pull request which you left and why.
